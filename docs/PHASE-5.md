# Phase 5 — Authentication and role-based access

## Delivered

- Auth.js credentials sign-in with encrypted JWT sessions.
- Eight-hour session lifetime.
- Password verification using bcrypt hashes.
- No public sign-up route.
- Login and sign-out flows.
- Protected dashboard routes.
- Database-backed active-account and role checks.
- Central permission matrix for Admin, Warden and Staff.
- Admin-only user directory API and role-protected hostel read API.
- One-time administrator bootstrap command; no credentials are committed.
- Prisma migration adding the password hash column.

## Role matrix

| Capability | Admin | Warden | Staff |
|---|---:|---:|---:|
| Read user directory | Yes | No | No |
| Read hostels | Yes | Yes | Yes |
| Manage hostels | Yes | Yes | No |
| Read participants | Yes | Yes | Yes |
| Manage participants | Yes | Yes | No |
| Read allocations | Yes | Yes | Yes |
| Manage allocations | Yes | No | No |
| Read reports | Yes | Yes | Yes |

The permission matrix is centralized in `src/lib/authz.ts`. Route handlers must call `requirePermission`; hiding a UI control is never considered authorization.

## Local setup

1. Start PostgreSQL and apply the previous database migration.
2. Update `.env` with a real local-only `AUTH_SECRET` generated by `npx auth secret`.
3. Apply the Phase 5 migration:

   ```bash
   npm run db:migrate:deploy
   npm run db:generate
   ```

4. Set the one-time bootstrap values in your local `.env`:

   ```dotenv
   BOOTSTRAP_ADMIN_EMAIL="admin@example.edu"
   BOOTSTRAP_ADMIN_NAME="System Administrator"
   BOOTSTRAP_ADMIN_PASSWORD="use-a-unique-password-of-at-least-14-characters"
   ```

5. Create the first administrator:

   ```bash
   npm run auth:create-admin
   ```

6. Remove the three `BOOTSTRAP_ADMIN_*` values from `.env`, then start the app:

   ```bash
   npm run dev
   ```

7. Open `http://localhost:3000/login` and sign in with the account you provisioned.

The bootstrap command hashes passwords using bcrypt (cost factor 12). Re-running it for the same email updates that account and assigns the Admin role; use it only when intentionally provisioning or recovering an administrator account.

## API examples

- `GET /api/admin/hostels`: signed-in users with hostels-read permission.
- `GET /api/admin/users`: Admin only.

Unauthenticated API requests receive HTTP 401; signed-in users without the required permission receive HTTP 403. Responses do not expose password hashes.

## Security boundaries

- Never commit `.env`, real passwords, password hashes or real student records.
- Do not use the Compose database password or example credentials in production.
- No public account creation or password-reset flow exists.
- Role and active status are re-read from PostgreSQL for protected server operations, so a disabled account or changed role does not rely solely on stale JWT claims.
- Production deployment still needs rate limiting, monitoring, MFA or institution SSO, account recovery, secure secret management and an explicit security review before real student data is used.
- The legacy static prototype remains outside this authentication boundary and must not be used for real student records.
